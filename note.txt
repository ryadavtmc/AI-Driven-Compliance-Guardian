 Project Workflow: AI-Driven Compliance Guardian

1. Business Understanding & Requirements
	•	Define compliance goals: Detect & block PII, PHI, secrets, credentials.
	•	Define output: Middleware should either block, mask, or flag sensitive input/output before reaching the LLM.
	•	Compliance frameworks to consider: GDPR, HIPAA, PCI-DSS.

⸻

2. Data Collection
	•	PII / Financial Text
	•	Banking / financial chat datasets (SGD – Banks domain, call-center, etc.).
	•	Augment with synthetic PII (emails, SSNs, phone numbers, card numbers) using Faker.
	•	Secrets / Credentials
	•	SecretBench (GitHub secrets dataset).
	•	Generate extra synthetic secrets (API keys, tokens) with regex + Faker.
	•	Create labeled datasets: sensitive vs. non-sensitive text.

⸻

3. Data Preprocessing
	•	Normalize text (lowercasing, punctuation handling).
	•	Tokenization (e.g., spaCy, Hugging Face).
	•	Annotate data with BIO tags (Begin-Inside-Outside) for sequence labeling of PII/secrets.
	•	Split into train/validation/test sets.

⸻

4. Detection Engine (Hybrid Approach)
	•	Regex Rules: Quick detection of structured PII (emails, SSNs, phone numbers, card numbers, AWS keys).
	•	ML / NLP Models:
	•	Option A: Traditional ML (Logistic Regression, Random Forest, etc.) with TF-IDF for classification.
	•	Option B: Sequence models (BiLSTM-CRF, BERT/DistilBERT) for token-level PII/secret detection.
	•	Combine both in an ensemble → higher precision + recall.

⸻

5. Middleware Layer
	•	Build a lightweight API wrapper (e.g., FastAPI/Flask).
	•	Middleware pipeline:
    User Prompt → Middleware → [PII/Secret Detection] → (Mask/Block/Allow) → LLM → Response

	•	Actions:
	•	Mask sensitive parts (replace with [REDACTED]).
	•	Block request if highly risky.
	•	Allow safe requests.

⸻

6. Evaluation
	•	Metrics: Precision, Recall, F1 for detection.
	•	Test on mixed safe vs. unsafe prompts.
	•	Benchmark regex-only vs. hybrid model.

⸻

7. Deployment & Integration
	•	Deploy as an API service (Docker, local or cloud).
	•	Integrate with an LLM (e.g., OpenAI API or open-source model).
	•	Add logging & dashboards (track blocked/flagged attempts).

⸻

8. Documentation & Reporting
	•	Project report (for CS703).
	•	Visual diagrams (workflow + architecture).
	•	Demo notebook or API script.


How We’ll Build the Project

Step 1: Clarify the Use Case
	•	Problem: Users may share sensitive data (PII, PHI, secrets, credentials) with an LLM.
	•	Solution: Insert a middleware filter between the user and the LLM.
	•	Middleware role: Detect → Mask/Block → Forward safe text.

⸻

Step 2: Gather Training + Testing Data

We need data that contains examples of sensitive info and safe info.
	•	For PII/Financial text
	•	Use banking/chat datasets (e.g., SGD – Banks domain).
	•	Inject synthetic PII with Faker (emails, SSNs, credit cards).
	•	For Secrets/Credentials
	•	Use SecretBench (real GitHub secrets).
	•	Add synthetic secrets (AWS keys, Slack tokens, etc.) with regex + Faker.

👉 Outcome: A labeled dataset: Sensitive vs Non-Sensitive.

⸻

Step 3: Preprocess & Label
	•	Clean the text (lowercase, strip extra symbols).
	•	Tokenize sentences/words (spaCy, HuggingFace).
	•	Annotate with BIO tags if doing token-level detection.
	•	Train/test split (e.g., 70/15/15).

👉 Outcome: Ready-to-train datasets.

⸻

Step 4: Build the Detection Engine

We’ll use a hybrid approach:
	1.	Regex rules
	•	Fast, accurate for structured patterns (emails, SSNs, AWS keys).
	•	Example: r"\b\d{3}-\d{2}-\d{4}\b" for SSNs.
	2.	ML/NLP models
	•	Detect contextually sensitive text (e.g., “my account number is …”).
	•	Start simple (Logistic Regression + TF-IDF).
	•	Then test advanced (BERT/DistilBERT for sequence tagging).
	3.	Ensemble
	•	Combine Regex + ML → better coverage.

👉 Outcome: A model that can spot PII/secrets in text.

⸻

Step 5: Middleware Implementation

We’ll wrap detection inside an API service (FastAPI or Flask).

Pipeline:
User Prompt → Middleware → Detection Engine
      → If sensitive → Mask/Block
      → Else → Pass through
→ Send safe prompt to LLM


	•	Masking example:
Input: "My SSN is 123-45-6789"
Output: "My SSN is [REDACTED]"
	•	Blocking example:
Input: "Here is my AWS key: AKIA...."
Output: "⚠️ Sensitive info detected. Prompt blocked."

👉 Outcome: Middleware ready to sit in front of any LLM API.

⸻

Step 6: Evaluation
	•	Test with real + synthetic test prompts.
	•	Measure Precision/Recall/F1.
	•	Compare:
	•	Regex-only
	•	ML-only
	•	Hybrid system

👉 Outcome: Benchmark results for your report/demo.

⸻

Step 7: Deployment
	•	Containerize with Docker.
	•	Deploy locally (Mac mini) first.
	•	Later: Deploy on cloud (AWS/GCP) if needed.
	•	Add logging (track blocked attempts).

👉 Outcome: Working system demo + deployment notes.

⸻

Step 8: Documentation & Report
	•	Architecture diagram (flowchart).
	•	Explain dataset sources, models, methods.
	•	Include ethical/legal compliance notes.
	•	Demo notebook + project report (for CS703 submission).

⸻

✅ So in simple terms:
Data → Detection Engine (Regex + ML) → Middleware API → LLM

################ MODELS ########################
 Models / Components for the Project

1. Regex-Based Detector (Rule Engine)
	•	Purpose: Catch structured PII/secrets fast (emails, SSNs, AWS keys).
	•	Technology: Python regex package.
	•	Role: Baseline system + part of hybrid model.

⸻

2. Traditional ML Classifier (Text Classification)
	•	Purpose: Detect whether a whole prompt is safe or unsafe.
	•	Models: Logistic Regression, Random Forest, XGBoost.
	•	Features: TF-IDF, n-grams.
	•	Role: Lightweight, explainable, easy to benchmark.

⸻

3. Sequence Labeling Model (NER-style)
	•	Purpose: Detect exact tokens (word-level) that are PII/secrets.
	•	Models: BiLSTM-CRF or BERT/DistilBERT fine-tuned for NER.
	•	Role: More precise than classification — identifies what part of text is sensitive.

⸻

4. Hybrid Ensemble
	•	Purpose: Combine Regex + ML classifier + NER.
	•	Logic:
	•	Regex fires → immediate block.
	•	NER highlights sensitive tokens → mask them.
	•	Classifier checks overall prompt risk.
	•	Role: Final detection engine inside middleware.

⸻

🔹 Final Architecture
User Prompt 
   → Regex Detector (quick catch)
   → ML Classifier (safe vs unsafe)
   → NER Model (highlight sensitive tokens)
   → Decision Engine → [Block / Mask / Allow]
   → Forward safe prompt to LLM
